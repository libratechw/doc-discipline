# doc-discipline

プロジェクト文書の作成・更新・整理の規律をまとめたエージェント用スキルです。
README、`docs/`、仕様書、コード内のコメントを対象とします。

## 何を扱うか

文書をコードと同じ基準（理解しやすい、正しく変更しやすい、保守できる）で設計します。
放っておくと文書は腐り、実装と食い違った時点で害になります。

**何を書くか。** これから作業する人が知っている必要がある情報だけを書きます。
Git 履歴を見れば分かることは書きません。線引きは「決定と理由は残す。決定に至る過程は残さない」です。

**どう構成するか。** 1文書1役割、1事実1か所。禁止するのは同じ事実の独立した二重所有です。
正本から機械的に導出される投影は複製にあたりません。

**コードを変えたら文書を合わせる。** 同じコミットの中で整合を取ります。後で直すと必ず忘れます。

**食い違っていたら。** 仕様の食い違いは実装者が決めることではないので、
黙って書き換えずユーザーへ確認します。リネームへの未追従やリンク切れはその場で直します。

## 一時的な文書を残さない

作業指示書、レビュー記録、検証手順書をリポジトリへ残さないことを求めます。
そこで確定した事実だけを正本へ反映し、文書自体は消します。

役割を失った文書も同じです。別の正本へ吸収された、誰も参照しない、
内容の大半が履歴や進捗になった文書は、事実を移して削除します。「念のため」は残しません。

## 使い方

`SKILL.md` は Claude Code、Codex、opencode が共通して読める形式です。
各ツールのスキル探索先へ、このリポジトリを置くか symlink します。

```
~/.claude/skills/doc-discipline/SKILL.md
~/.codex/skills/doc-discipline/SKILL.md
~/.config/opencode/skills/doc-discipline/SKILL.md
```

## 関連するスキル

このスキルは、どの文書が何を持ち、いつ消すかを扱います。
決まった内容をどう書くかは [japanese-technical-writing](https://github.com/libratechw/japanese-technical-writing) が扱います。

- [japanese-technical-writing](https://github.com/libratechw/japanese-technical-writing) — 日本語実用文の書き方。順序、命名、強調、図表の選び方
- [design-review](https://github.com/libratechw/design-review) — 設計と実装のレビュー基準

## 貢献

規則の追加や修正の提案を歓迎します。

提案には、その規則がない状態で実際に何が起きたかを添えてください。
現在の規則で防げているなら、追加せずに済みます。
